# Dedicated web admin console implementation

The React application now has a separate lazy-loaded staff console at `/admin`, with the supplied desktop dashboard as its visual foundation. Staff enter at `/admin/login`. The storefront keeps its own layout. The administration shell has a collapsible sidebar, workspace breadcrumbs, order/customer/shipping-reference search, permitted action queues, current staff identity and server logout. Sidebar links and protected pages use capabilities returned by Spring Boot; every API separately authorizes the caller.

Orders is the single sidebar entry for order and shipping work. Legacy `/admin/fulfillment` links replace-redirect to `/admin/orders` while retaining query parameters and anchors; the legacy entry retains its `shipments.write` gate. Canonical order pages retain `orders.read`. Shipment preparation, provider commands and shipping retries retain the existing Admin/Fulfillment role checks and server authorization; read-only staff can inspect shipment history without requesting provider command access. Each order groups delivery/items/cancellations, Shipping / Fulfillment, and payment/commercial information into separate sections. Dashboard-workflow orders describe automatic preparation and Shiprocket operations; assisted orders retain explicit package preparation.

The queue follows the supplied Orders PDF's structure: quick All/Confirmed/COD due/Paid/Cancelled filters, search/date filters, state selectors, customer initials, colored status badges and compact shipping records with expandable saved details. Counts are explicitly scoped to the currently loaded filtered page, including today's orders in Asia/Kolkata, COD-due orders (not a monetary collection balance), fulfillment-status remainders and cancelled orders. Pagination shows returned row ranges without inventing a total. Export page CSV downloads only the loaded page, quotes values and neutralizes spreadsheet formulas. No aggregate-count, full-dataset-export or provider API contract was added. Automatic preparation/recovery alerts remain accessible below the queue.

## Data and permission contracts

Customer list/detail responses determine email visibility from the authenticated server principal: `ADMIN` receives full emails (`emailMasked: false`), including when also assigned Support; `SUPPORT` receives masked emails (`emailMasked: true`). Phone masking is unchanged. The server grants `customers.email.reveal` to Admin and Support under the existing role model. An explicit CSRF-protected `POST /api/v1/admin/customers/{id}/reveal-email` returns `{email}` only after recording `CUSTOMER_EMAIL_REVEALED` with the staff actor and customer reference in the same transaction. Audit failure prevents disclosure; audit metadata never contains the customer's email. Missing/non-customer targets return 404. Customer list, detail and reveal responses send `Cache-Control: no-store`.

The Customers UI offers permitted support staff Reveal email and Hide email in both list and detail views. Reveals run only on an explicit click, have loading/error/retry states, and stay in local component memory rather than shared query or browser storage. Customer/page/search/session changes and permission loss reset the revealed view. Customer query keys include staff identity and roles to prevent reuse of an Admin projection for a different actor. This policy applies to Customers; existing order-operation contact projections retain their separate permissions.

`GET /api/v1/admin/capabilities` returns the caller's role grants and granular capabilities. Unknown grants fail closed. `/admin/dashboard?days=7|30|90` returns `asOf`, the bounded date window, INR, `Asia/Kolkata`, exact metric definitions and only authorized projections. Financial values are aggregated from persisted snapshots and ledgers, never calculated from downloaded order pages.

Reporting semantics are explicit: booked merchandise is the net saved merchandise line total; online captures and confirmed online refunds are the current ledger position for orders created in the selected window, because no capture-event timestamp contract exists yet. These values are not labeled as cash movement during that interval. COD and pending refunds remain separate. Action queues span current unresolved records across all dates. Test/demo database fixtures are included and the environment notice identifies development profiles. Unsupported metric values render as unavailable.

Operations retain `/api/v1/admin/operations/**`; catalog retains `/api/v1/catalog/admin/**`. New administration reads/commands use `/api/v1/admin/{customers,staff,roles,settings,promotions,audit}`. Settings apply only at their effective time; checkout captures the current return promise and monetary/tax snapshots. `/api/v1/public/business-policy` exposes only the current public shipping and return terms.

The operations order queue accepts a literal, case-insensitive `search` of up to 254 characters across order number, the ordering account's name/email/phone, provider order/shipment IDs and AWB/tracking references. State/date filters and pagination still apply to orders, including when several bookings match. Its additive `customer` and `shipments` fields are available only to existing operations-reader roles; Finance/Reporting retain their separate ledger projection. Shipping summaries load in one batch for the current page and preserve cancelled, replacement and split records. Customer identity comes from the current account, not the immutable delivery-recipient snapshot. Provider status and its timestamp describe the latest saved verified observation; refreshing the queue does not make a live Shiprocket request. Direct Shiprocket dashboard links are deferred at the owner's request.

Categories have a Delete action beside Edit. Its confirmation names the category and slug; failed deletion preserves the row and editor draft. `DELETE /api/v1/catalog/admin/taxonomy/categories/{id}` requires Admin authorization, CSRF and an `expectedName`/`expectedSlug` request body. The backend locks the category, rejects a changed record with 409, and blocks deletion while any product (including draft/archived), child category or included/excluded promotion rule still references it. Deactivate the category or reassign/remove those references first. An already-absent category returns 204 for a safe lost-response retry; an unavailable endpoint remains an error in the UI. Successful deletion and its audit event commit together. Promotion configuration and deletion share the existing advisory lock so concurrent promotion saves cannot create orphan references. Existing order and business-policy snapshots remain unchanged; no schema migration is needed.

The category dialog also offers **Move products to another category**. Staff must explicitly choose a different active replacement and confirm **Move products and delete**. This sends optional `replacementCategoryId` with the existing deletion contract. The backend checks child-category and promotion references before moving anything, locks the active replacement against removal/deactivation, and moves all source products and deletes the source category in the same transaction. Each move is audited and increments the product version so stale editor saves cannot overwrite it. Publication status, product details, variants, stock, reservations and historical orders remain unchanged; future category-based promotion and return rules follow the replacement. No replacement is chosen automatically. Missing/inactive replacements and remaining child/promotion references reject the entire operation. Retrying after a confirmed source deletion remains a harmless 204.

Archive is an explicit command for both drafts and published products, including incomplete drafts, and does not validate or save unrelated editor fields. Its confirmation explains retained category/inventory/order references and any unsaved changes being discarded; cancellation or failure preserves the draft. Metadata saves keep an archived product archived and use the editor's Save changes action. Unpublished descriptions may remain blank, matching the backend draft contract; publication keeps its existing validation gates. Archiving retains the category link. To release it, delete the product from the product list or reassign it; categories can alternatively be deactivated.

The product list exposes a separate **Delete** action for draft, published and archived products. Confirmation names the product and SKU and explains that removal from the catalog cannot be undone, releases the category, preserves inventory/order history and does not write off stock. Admin/CSRF-protected `POST /api/v1/catalog/admin/products/{id}/delete` requires `expectedName`, `expectedSku` and `version`. It rejects stale identity/version, included/excluded promotion references (including inactive rules), positive reserved quantities or active reservation records. Inventory rows are locked in checkout's variant order before reservation checks. The product is marked deleted, disabled, detached from its category and versioned in the same transaction as `PRODUCT_DELETED` audit. Already missing/deleted targets return 204 with no duplicate event.

V38 adds `products.deleted_at` and permits a null category only for a disabled, archived deletion record. Deletion is catalog removal with a retained database record, rather than erasure of inventory/commercial records: variants, SKU identity, stock, movements, audits, reservations and historical snapshots remain intact. Hibernate's product restriction excludes deleted records from all repository reads, admin publication filters, metadata editing, cart and checkout availability; native promotion validation also rejects them. Historical shipping measurements and inventory movement names remain available through existing native history queries. No restore/purge API or automatic deletion of user data is added. The existing legacy DELETE-as-archive endpoint keeps its behavior for compatibility. Restart the backend to apply V38 and load the new command; deploy updated code consistently before using deletion so an older application instance cannot serve retained rows.

Normal-profile checkout requires approved real GST classification, the effective rate and current seller/price policy. `demo` and `payment-sandbox` profiles retain fixture workflows. Synthetic identifiers cannot receive production tax approval. Saving configuration or approving its tax treatment does not establish production readiness or generate a valid invoice.

Staff access changes increment durable `users.auth_version`; real browser principals carry their version and the request filter rejects stale/disabled sessions. The Redis namespace is now `ecommerce:session:v2`, which deliberately requires existing users to sign in again after upgrade. Browser-authenticated commands retain CSRF protection; API requests have timeouts and request IDs. No raw session tokens are stored in browser storage.

## Database and storage setup

Flyway applies additive migrations V24–V28: catalog versions/taxonomy/variants/publication/thresholds, effective business policies and tax approvals, authorization versions, promotion usage and image-upload receipts. Do not edit migrations once applied; use a forward migration for further changes.

Image upload uses a signed PUT and server-side confirmation before adding its URL to the draft. Configure all six server-only variables to enable S3-compatible storage:

- `CATALOG_STORAGE_ENDPOINT`
- `CATALOG_STORAGE_BUCKET`
- `CATALOG_STORAGE_REGION`
- `CATALOG_STORAGE_ACCESS_KEY`
- `CATALOG_STORAGE_SECRET_KEY`
- `CATALOG_STORAGE_PUBLIC_BASE_URL`

The public base URL must serve the bucket's object-key root. Configure bucket CORS for the web application's origin and the headers returned by the signing API. JPEG, PNG and WebP uploads are bounded to 5 MiB. Signing binds the exact file, receipt, media type and length; conditional writes prevent overwrites. Confirmation verifies object metadata and bounded bytes/checksum, ownership and expiry, and is safely repeatable. Redirects are not followed. S3 configuration errors and provider failures remain explicit; no real bucket or provider settings were changed during implementation.

`CATALOG_STORAGE_MODE=AUTO` now selects PostgreSQL uploads when all S3 settings are absent. Partial S3 configuration still fails closed; `DATABASE` explicitly selects PostgreSQL and `S3` explicitly selects S3-compatible storage. Migration V40 stores optimized bytes separately from product rows, and the Admin uploader uses authenticated multipart requests with CSRF and a retry UUID. Database images are decoded/re-encoded to bounded JPEG/PNG, resized to at most 1,600 pixels per side, and served by a cached endpoint only to Admins or through active product references. Existing S3/manual URLs remain supported. See [storage and capacity details](../java-ecommerce-app/README.md#product-publication-and-image-storage).

Publication requires a description, primary image, active category, positive selling price, active HSN/SAC classification with a current GST rate, and positive whole-number unit weight/length/width/height. SKU uniqueness and nonnegative integer inventory remain enforced; stock zero is allowed. Drafts retain the core name/category/SKU/price requirements but may omit description, image, tax and shipping. Invalid fields show links to editor sections. Creating a draft and subsequently failing publication opens the saved draft rather than creating another product on retry. Existing published products are not automatically unpublished by the migration; their next metadata save/publication must meet the new rules.

## Verification and release boundaries

Execution results belong in `IMPLEMENTATION-TRACKER.md`. Component/API tests cover staff permissions and deep links, dashboard/error states, pagination boundaries, stock conflicts/idempotency, draft/publication, GST, staff safeguards/session revocation, policy snapshots, promotions and uploads. The integration suite uses a separate local PostgreSQL database.

Real carrier booking/labels/reverse pickup, real Razorpay acceptance, invoice/credit-note document output, seller/finance/tax acceptance, privacy/retention decisions, production security/MFA/rate limits, outbox operations, deployment and backup-restore evidence remain production release gates. Building the administration modules does not close these external or operational gates.
